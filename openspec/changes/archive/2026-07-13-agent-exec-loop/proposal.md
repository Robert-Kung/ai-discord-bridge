## Why

The bridge today is a safe intercom, not a working agent: every `@`-mention is one synchronous `claude -p` with a 300 s kill-timeout, no progress output, no cancellation, and locks that stall the whole bot behind one task. The execution tier (`acceptEdits`) can edit files but cannot run shell — so the agent can change code it can never test, the exact "marks features done without end-to-end verification" failure mode. And edits land directly on the live mounted project dirs with no branch, no diff review, no merge gate. The operator's goal — "open a Discord message, get a harness-grade agent that changes code, generates ideas, solves problems" — is blocked by the execution model for the observability/job/git milestones; the verification and shell milestones are **security-boundary changes** and are gated as such (review D3: verification is agent-influenced execution; Bash relaxation swaps action-level containment for outcome-level containment).

## What Changes

- **Background job model (milestone 1)**: execution-tier tasks run as tracked background jobs (in-memory registry + on-disk job file). New commands: `!jobs` (list, with status/age), `!cancel <id>` (kill the subprocess **group**, escalating TERM→KILL). Conversation calls no longer queue behind a long-running exec task. `!jobs`/`!cancel` enter `HELP_TEXT`/`STARTUP_ANNOUNCEMENT` in this milestone, not at wrap-up.
- **Streaming progress (milestone 1)**: exec-tier calls switch to `--output-format stream-json --verbose` (the CLI hard-fails without `--verbose`; verified on 2.1.199); the bridge maintains one status message per job — posted as a **reply** to the originating message, carrying the job id and a literal `!cancel <id>` hint — edited with a rolling tool-use trace.
- **Per-tier timeouts (milestone 1)**: conversation keeps `CLAUDE_TIMEOUT`; exec jobs get a much larger `EXEC_TIMEOUT`; timeout and cancel kill the whole process group (today `proc.kill()` orphans grandchildren) and report the worktree state instead of discarding silently.
- **Git task loop (milestone 2, the new safety gate)**: every execution-tier task runs on a dedicated git branch/worktree created from HEAD — never on the live checkout. The bridge commits the result to `bridge/<job-id>` (the **branch, not the worktree, is the recoverable source of truth**), posts `git diff --stat` inline plus the full diff as a file; ✅ merges under a strict protocol (clean live tree required, `merge --abort` on conflict, exact recovery commands reported), ❌ discards. **Reaction timeout parks the job as awaiting-review (`!merge <id>` / `!discard <id>`) — completed work is never auto-deleted.**
- **Attachment ingestion (milestone 3)**: whitelisted-user attachments (screenshots, logs, error dumps) are downloaded — sanitized basename, size/count caps, stored **outside** the repo worktree — and their paths injected into the prompt as delimited untrusted content.
- **Verification + exec-tier shell (milestone 4 — gated on `egress-exec-isolation` phase 2)**: after an exec task, the bridge runs a per-project test command **configured outside the repo** (in `discord-state`, never read from the worktree — the agent must not author its own verify command) inside the worktree, with a stripped env and timeout, and appends pass/fail + output tail. No green claim without a run; absent config → "not configured". In the same milestone, the exec tier runs with Bash permitted — **only inside the phase-2 executor container that mounts the job worktree (plus credential) and nothing else**, so the diff gate actually covers the writable surface. Both features are the same trust decision (agent-grade code execution) and share one gate. Rationale (review, verified): in the single-container posture the diff gate cannot see writes to the 10 rw project mounts, the bot config dirs (`CLAUDE.md` = persistent prompt injection), or `discord-state`; settings.json has zero Write/Edit denies; and egress phase 1 still allows Discord webhooks — `cat` a credential + webhook POST is a complete exfil chain.
- **Dual-account evaluator (milestone 5, optional)**: before requesting the human ✅, the other bot reviews the diff with a deliberately-skeptical review prompt and posts findings — generator/evaluator split on the existing A/B pair. Advisory only; feature-flagged off by default.

## Capabilities

### New Capabilities
- `exec-task-loop`: branch/worktree isolation for execution-tier tasks, diff-review merge gate with a safe merge protocol, post-task verification run (gated), attachment ingestion into the job workspace.
- `exec-jobs-observability`: background job registry with list/cancel, streaming progress surface, per-tier timeouts with process-group kill semantics, restart recovery (orphan marking, awaiting-review re-post).

### Modified Capabilities
- `execution-permissions`: the execution tier's Bash posture changes from "denied by omission in headless `acceptEdits`" to "permitted **only inside the phase-2 executor container** (worktree-only mounts) once `egress-containment` phase 2 is proven"; the plan-then-execute bypass flow's role shifts to legacy for coding tasks.
- `agent-trust-layers`: the execution layer gains the job/worktree lifecycle; the chokepoint contract extends to streaming output. Conversation-layer guarantees are unchanged. **Project identity (sessions, notes, locks) is decoupled from subprocess cwd** so a worktree cwd does not orphan the project's memory.

## Impact

- **Code**: `bridge/runner.py` (stream-json parsing incl. session/token accounting, process groups, job registry), `bridge/frontend.py` (status-message editing, `!jobs`/`!cancel`/`!merge`/`!discard`, attachment download, file replies), git worktree helpers, per-project verify config in `discord-state`.
- **Dependencies**: `bridge-restructure` lands first (this change touches every layer). Milestone 4 (verification + Bash) depends on **`egress-exec-isolation` phase 2** — not merely a green phase-1 canary.
- **Sequencing (resequenced at review)**: jobs+streaming+timeouts → git loop → attachments → verification+Bash (phase-2-gated) → evaluator. Milestone 1 is zero-security-surface and builds the registry the git loop hangs off.
- **Out of scope**: multi-channel routing, MCP tool servers for the agent, autonomous scheduling. The `approve` tier stays as-is for non-git one-shot commands.
